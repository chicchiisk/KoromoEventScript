# RuntimeValue を値型として扱う

- ADR: 0005
- ステータス: 採用
- 日付: 2026-07-20
- 関連 Issue: 性能改善計画 4
- 関連仕様: `docs/spec/k-intermediate-representation-spec.md`、`docs/spec/unity-runtime-spec.md`

## 背景

VM は算術、比較、変数ロード、配列操作のたびに `RuntimeValue` を生成する。従来の参照型では、単純な数値や真偽値にもヒープ割り当てが発生し、エラトステネスのふるいのような反復処理でGC負荷が支配的になっていた。

`RuntimeValue` は不変であり、実行中の値は種類とプリミティブ値または参照識別子だけで表現できる。セーブデータでは同じプロパティをJSONへ保存しているため、参照同一性を必要としない。

## 決定

共有Runtime Coreの `RuntimeValue` を、不変の `readonly struct` とする。公開プロパティ、生成メソッド、値等価性、JSONコンストラクターは維持し、WindowsとUnityで同一の表現を使用する。

## 検討した代替案

### 参照型のまま値をキャッシュする

真偽値や小さな整数は削減できるが、任意の数値演算結果は引き続き割り当てられる。キャッシュ範囲による挙動差も生じるため採用しない。

### VM内部だけ別の値型を使う

公開値との変換が命令境界やsyscall境界に増え、実装が二重化する。Runtime Core全体で値の意味が同じため採用しない。

## 判断理由

- 数値、真偽値、参照ハンドルの一時値をスタック上または配列内へ直接保持できる。
- 不変性と値等価性が既存のrecord契約に合う。
- JSONのプロパティ契約を維持でき、既存セーブデータと互換性がある。
- WindowsとUnityの共有ソース方針を崩さない。

## 影響

- `RuntimeValue?` はnullable参照ではなく `Nullable<RuntimeValue>` になるため、syscall戻り値を取り出す箇所では `Value` が必要になる。
- 構造体コピーが発生するため、将来フィールドを大幅に増やす場合はサイズを再評価する。
- JSON往復、値等価性、VMおよび永続化テストで互換性を継続確認する。

## フォローアップ

整数オブジェクトハンドルと型特化配列では、この値型表現を前提に参照および配列要素のサイズを最適化する。
