# 開発ワークフロー

このドキュメントは、KoromoEventScript を GitHub Issue、ブランチ、Pull Request、CI、人間レビューを軸に開発するための運用ルールを定義する。

本プロジェクトでは、実装作業の多くを AI が担当する前提とし、人間は Issue の粒度調整、仕様判断、PR レビュー、最終的な品質判断を担う。

## 基本方針

- 1つの Issue に対して、1つのブランチと1つの Pull Request を作成する。
- AI は Issue に書かれた範囲だけを実装する。
- 仕様変更が必要な場合、AI は実装を進める前に PR 本文またはコメントで提案する。
- Pull Request は人間がレビューしてから main へ取り込む。
- CI の成功を merge の必須条件とする。
- テストを追加できる実装では、原則として必ずテストを追加する。

## 役割分担

| 役割 | 主な責務 |
|---|---|
| 人間 | 仕様判断、Issue 作成、優先順位決定、レビュー、merge 判断 |
| AI | Issue 理解、ブランチ作成、実装、テスト追加、PR 作成、レビュー指摘対応 |
| CI | Markdown、ビルド、テスト、フォーマット、スナップショットの自動検証 |

## Issue 作成ルール

Issue は AI への発注書として扱う。
曖昧な Issue は、実装前に細分化または補足する。

Issue には次の項目を含める。

| 項目 | 内容 |
|---|---|
| 目的 | この Issue で達成したい状態 |
| 参照仕様 | 実装時に読むべき仕様書や関連 Issue |
| 実装範囲 | 変更してよい機能、モジュール、ファイル範囲 |
| 対象外 | この Issue では扱わないこと |
| 受け入れ条件 | PR レビューで確認する具体的な条件 |
| 必須テスト | 追加または更新すべきテスト |
| 依存 Issue | 先に完了している必要がある Issue |

## Issue の粒度

1つの Issue は、レビュー可能な大きさに保つ。
目安として、通常の実装 Issue は1つから3つ程度の主要ファイル変更に収める。

大きすぎる Issue の例:

- KES 言語処理系をすべて実装する
- CLI と VM と VS Code 拡張をまとめて作る
- Windows Runtime の UI 全体を作る

適切な Issue の例:

- `.ke` の行コメントとブロックコメントを字句解析する
- `label` と `jump` の構文を parser に追加する
- 未定義タグ参照を `KES2xxx` 診断として出力する
- `kes build --check-only` の終了コードを仕様に合わせる

## ブランチ運用

ブランチ名は、Issue 番号と作業内容が分かる名前にする。

```txt
feature/issue-12-parser-label-jump
fix/issue-34-diagnostic-location
docs/issue-8-testing-strategy
ci/issue-5-initial-ci
```

複数 Issue を1つのブランチでまとめて実装してはならない。
共通の前提作業が必要な場合は、先に別 Issue として切り出す。

## Pull Request 運用

Pull Request は、Issue の受け入れ条件を満たしたことを説明する場所として扱う。

PR 本文には次の項目を必ず書く。

- 対応 Issue
- 変更内容
- 参照した仕様
- 満たした受け入れ条件
- 実行したテスト
- レビューしてほしい点
- 対象外

PR は Draft として作成してよい。
AI が実装と自己確認を終えた段階で、レビュー可能な状態として人間に渡す。

## レビュー対応

レビュー指摘は、元の PR ブランチ上で対応する。
指摘対応中に新しい仕様判断が必要になった場合は、PR コメントで確認する。

レビュー対応時は、次を守る。

- 指摘された範囲を優先して直す。
- 関係のないリファクタリングを混ぜない。
- 追加で見つけた問題が大きい場合は、別 Issue に切り出す。
- CI が失敗している場合は、原因と修正内容を PR に追記する。

## 仕様変更の扱い

実装中に仕様と矛盾する点が見つかった場合、AI は独断で仕様を変えない。
次のどれかで対応する。

1. Issue の対象外として記録し、別 Issue を提案する。
2. PR 本文に仕様変更案を書き、人間レビューを待つ。
3. 仕様書の修正を同じ Issue の受け入れ条件に含める。

仕様書を変更した PR では、実装と仕様のどちらが主目的かを明確にする。

## Merge 条件

main への merge は、次を満たしてから行う。

- 対応 Issue が明記されている。
- 受け入れ条件を満たしている。
- 必要なテストが追加または更新されている。
- CI が成功している。
- 人間レビューで承認されている。

## ラベル運用

初期ラベルは次を想定する。

| ラベル | 用途 |
|---|---|
| `task` | AI が実装する通常タスク |
| `docs` | ドキュメント整備 |
| `ci` | CI、テスト基盤、開発基盤 |
| `parser` | 字句解析、構文解析 |
| `compiler` | 意味解析、型検査、IR 生成 |
| `vm` | VM 実行系 |
| `cli` | CLI |
| `runtime` | Windows / Unity / Unreal runtime |
| `vscode` | VS Code 拡張 |
| `blocked` | 依存関係により着手できない |

## AI への作業依頼例

```md
Issue #12 を実装してください。

- feature/issue-12-parser-label-jump ブランチを作成
- docs/spec/kes-language-spec.md と docs/spec/cli-tool-spec.md を参照
- 受け入れ条件を満たすテストを追加
- CI が通る状態で Draft PR を作成
```
